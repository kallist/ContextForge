# ContextForge V0.2 Retrieval Research

Status: **RESEARCH COMPLETE — DESIGN EVIDENCE, NOT V2 IMPLEMENTATION**

This document analyzes the frozen `contextforge-benchmark-v1` evidence and the production V1 retrieval/packing path. Statements are labeled `FACT`, `INFERENCE`, or `HYPOTHESIS`. No production ranking, packing, schema, CLI, or MCP behavior is changed by this research.

## 1. Executive Summary

`FACT` V1 does not have a simple “structural instead of lexical” pipeline. `searchRepository` already combines exact identity, indexed metadata, a generation-verified source scan, graph expansion, and weak Git signals. Its weakness is how those signals are interpreted and fused: common natural-language task terms can receive exact-symbol identity weight, lexical evidence is family-capped without a distinct-term coverage feature, structural candidates inherit score from noisy seeds, and every task uses the same ranking and packing policy.

`FACT` Across all 44 required files, the diagnostic replay found 43 in the lexical candidate set and all 44 in the structural Pack input top 64. Lexical ranked 23 required files ahead of structural V1; structural ranked 13 ahead; 7 tied; one lexical file was absent. Median required-file rank was 2 for lexical and 3.5 for structural. Sixteen of 24 tasks had at least one tied score in structural V1's top five.

`FACT` Both rankers attached only 33 of 44 required symbols to `relevantSymbols`, while V1 Pack ultimately covered 39 of 44 required symbol cores. Packing therefore has real recovery value, but file retrieval, symbol discovery, range selection, and section allocation are separate failure stages.

`FACT` The four ContextForge 8K required-context misses split into one primarily packing failure, one primarily retrieval failure, two combined retrieval-and-packing failures, and zero cases where the existing evidence is wholly insufficient. A fifth task preserved full recall but had materially worse precision than lexical.

`INFERENCE` V2 should not replace structural retrieval with the benchmark lexical baseline or retune V1 weights. It should retain one file envelope and the current safety/snapshot model, add deterministic task analysis and plan contracts, make identity/lexical/symbol/test/graph signals complementary candidate sources, apply ambiguity-aware fusion, and let a plan guide—but never override—the hard budget.

`HYPOTHESIS` This can address the observed V1 failures without embeddings, an LLM, a vector database, cloud services, or a schema migration in the first implementation slice.

## 3. Research Questions and Methodology

The study asked where each required file and symbol first disappeared, which evidence pushed competing candidates upward, whether Pack later recovered or dropped the context, and which V1 successes must not regress.

Method:

1. Verify `origin/main`, `v0.1.1`, the dataset lock, Gold counts, 360 reference cases, and four artifact hashes.
2. Read production task normalization, candidate construction, lexical scan, graph expansion, scoring, Pack planning, range selection, serialization, index generation, safety, benchmark adapters, and metrics.
3. Replay all 24 tasks at 8K through a benchmark-only, Gold-blind diagnostic projection. System code receives task/runtime/budget only; Gold is joined afterward by the analysis layer. The ignored, reproducible diagnostic output records the full task text, required/supporting Gold, ranks, evidence, Pack decisions, final ranges, all-budget V1 traces, and stage attribution; the committed failure matrix records the classification and evidence without duplicating that large artifact.
4. Reconcile every replayed selected-file identity with the frozen reference result for all three systems. A mismatch fails the diagnostic.
5. Record top candidates plus any required candidate, required file/symbol ranks, symbol-evidence presence, Pack selection/drop reason, all-budget ContextForge traces, and first/last stage facts.
6. Classify each task manually in `benchmarks/analysis/v0.2/failure-matrix.json`; validate task completeness, taxonomy, evidence, dataset identity, absence of absolute paths, and summary reconciliation.

The generated diagnostic is source-free, deterministic, bounded, and written only to ignored `.benchmark-output/`. It contains no source bodies or temporary absolute roots. Corpus application code is never executed and the analysis uses no network.

## 4. Actual V1 Pipeline

```text
Task
  → normalizeTaskQuery
  → indexed identity/metadata candidates
  → generation-verified source lexical evidence
  → fixed additive primary ranking
  → bounded file-graph expansion
  → capped evidence fusion and final ranking
  → first 64 candidates for Pack
  → fixed role/section allocation
  → symbol, Markdown, lexical, or prefix ranges
  → deterministic eviction and serialization
  → Context Pack
```

| Stage | Production owner | Input → output | Important V1 bounds/version | Existing observability |
|---|---|---|---|---|
| Task normalization | `src/core/task-query.ts` — `normalizeTaskQuery` | raw task → `TaskQuery.signals` | 16 KiB task; 256 signals; `task-query-v1` | normalized signals and low-information diagnostic |
| Direct candidates | `src/application/search-repository.ts` — `buildDirectCandidates` | snapshot metadata + signals → file envelopes | 32 matches per signal; 200 primary files | direct evidence and relevant symbols |
| Lexical evidence | `searchRepository` source scan | verified bytes → `SOURCE_LEXICAL` evidence | 10,000 files; 64 MiB; 120 lexical candidates | scan counts, stale/partial diagnostics, evidence |
| Primary scoring | `src/core/ranking/structural-v1.ts` | evidence → capped relative points | identity 150, lexical 120, structural 65, Git 5 | score contributions and reasons |
| Graph expansion | `searchRepository` — `expandCandidates` | top seeds + graph → inherited evidence | 24 seeds; depth 2; 24 neighbors; 128 new files | origin, graph distance, expansion reasons |
| Final ranking | `rankBuilder` / `compareRanked` | fused file envelopes → ordered candidates | 256 internal; public search 20 default; Pack 64 | rank, score, reasons, nested symbols |
| Pack planning | `src/application/build-context-pack.ts` | top 64 + snapshot → selected representations | fixed role shares/item caps; 64 files; 32 MiB | manifest selections, roles, drops |
| Range selection | `buildRepresentations` | candidate + source → whole/symbol/lexical/doc ranges | 2/4/6 relevant symbols; 3/8 surrounding lines | selected ranges and relevant symbols |
| Serialization | `renderContextMarkdown` + final reduction | section plan → Markdown | exact estimator budget; bounded eviction | payload tokens, reductions, partial status |

The one-generation invariant is preserved throughout: Search loads one complete SQLite snapshot N; verified bytes must match N; Pack continues on N even if a writer activates N+1.

## 7. Deep-dive Worst Cases

### `self-index-activation-race`

`FACT` The lexical baseline placed `sqlite-index-repository.ts` first and `build-index.ts` at 21. Structural V1 placed them at 10 and 18; both required symbols were present. Four structural top candidates were tests at 320–335 points. Common task words such as `active`, `generation`, and `written` matched local symbols as exact identity, then test/import relations reinforced those seeds.

`FACT` Pack selected four high-ranked test files and multiple primary files, then dropped both required files with `SECTION_LIMIT`. The last stage with both required symbols was final ranking; the first loss was Pack planning.

`INFERENCE` This is not solved by deeper graph traversal. V2 needs ambiguity-aware identity scoring, task concepts for concurrency/writer boundaries, and a plan that protects more than the single top file when several implementation owners are evidenced.

### `self-stale-lexical-source`

`FACT` `search-repository.ts` was structural rank 5 with the required `searchRepository` symbol relevant, but selected ranges omitted its core. `repository-source-reader.ts` was rank 8, yet `FileSystemRepositorySourceReader.readTextFile` was not relevant. Both files were packed, so file recall was 1.0 and symbol recall 0.

`FACT` The benchmark materialization is clean. No stale bytes were ranked and the correct generation-verification behavior did not cause this miss.

`INFERENCE` One miss is lexical-file-to-owning-symbol propagation; the other is range selection from an otherwise correct symbol-bearing file. A future regression fixture may mutate source to test stale safety, but the frozen quality task must not be rewritten.

### `self-package-parser-assets`

`FACT` Lexical ranked `scripts/package-smoke.mjs` first; structural ranked it 13. The file and `package.json` were packed. The required top-level symbol `run` was not marked relevant by either ranker because the task did not name `run` and source lexical matches are file-level only.

`INFERENCE` Symbol V2 should map verified lexical match locations to enclosing symbols and treat a common symbol name as ambiguous unless file/path/task evidence narrows it. It should not give every `run` declaration a strong identity boost.

### `self-pack-snapshot-architecture`

`FACT` The required ADR was lexical rank 5 and structural rank 41. Structural top ranks were tests or helpers boosted by common exact symbols such as `active` and `source`. Pack accepted 64 candidates but selected another architecture slice and dropped the required ADR with `SECTION_LIMIT`.

`INFERENCE` The first benchmark retrieval miss is at the top-20 boundary, but the production Pack failure completes later at section allocation. This case is therefore both retrieval and packing, not only “the graph missed a document.”

### `self-output-publish-race`

`FACT` The required adapter was lexical rank 2 and structural rank 6. Both systems covered the required symbol, but ContextForge precision was `.125727` versus lexical `.222582`. Structural top five were dominated by test files matching common symbols such as `output`, `after`, and `concurrent`.

`INFERENCE` This is a precision/fusion problem, not a recall failure. A V2 gate must preserve the required file while reducing generic identity/test noise.

## 8. Success Cases to Preserve

- Exact symbols: `self-pack-exact`, `ts-session-revoke-exact`, `py-release-stale-exact`, and `mixed-client-update-exact` show exact qualified symbols plus symbol slicing can be decisive.
- Cross-file behavior: `ts-logout-token-bug`, `mixed-stale-profile-cache`, and `mixed-rename-reverts` show imports/relationships can recover owners that literal retrieval misses or ranks later.
- Test-led tasks: all three `TEST_FAILURE` tasks reached complete required-symbol recall; existing direct test imports and test/source edges must remain available and labeled by confidence.
- Ambiguous tasks: `ts-users-stay-signed-in` and `mixed-rename-reverts` show relationship evidence plus Pack can improve precision without exact identities.
- Configuration/YAML: `mixed-openapi-display-name` proves V1 can combine a structured-code symbol with a non-symbol Gold range.
- Hard-budget recovery: V1 Pack covered 39 required symbol cores although only 33 appeared as relevant symbols in each retrieval system; small whole files, lexical fallback ranges, and bounded semantic slices remain valuable.

## 9. Why Lexical Wins

`FACT` Among 43 required files present in both candidate sets, lexical rank was better on 23 files, structural on 13, with 7 ties; structural also found one required file absent from lexical. The largest lexical advantages were the weak self-repository cases: rank 1 vs 10 for the SQLite writer, 1 vs 13 for package smoke, 5 vs 41 for the packing ADR, and 2 vs 6 for output publication.

Reasons:

- It rewards several distinct task literals across the entire verified file without sharing one 120-point lexical family cap with metadata evidence.
- Repeated technical phrases and local prose can accumulate discriminative evidence even when no symbol name matches.
- It avoids graph inheritance from a bad seed and does not turn every test relationship into additional relevance.
- On the self corpus, task wording often appears directly in implementation comments, diagnostics, ADR prose, or tests.

Safe V2 concepts to reuse:

- generation-verified source reads and exact byte hashing;
- exact path/basename/qualified-symbol/error/technical-literal evidence;
- distinct non-low-value term coverage;
- bounded occurrence saturation;
- local comments and documentation as labeled lexical evidence;
- match locations that can be mapped to enclosing symbols.

Benchmark-only behavior not to copy:

- `LEXICAL_BASELINE` numeric weights and its unreviewed score scale;
- whole-file packing and skip-if-does-not-fit behavior;
- concatenating all task signals without task mode, ambiguity, or candidate-source provenance;
- any baseline-specific serializer or instruction competition.

## 10. Why Structural V1 Loses

1. `FACT` `buildDirectCandidates` applies exact-symbol matching to every non-low-value query signal. Ordinary natural words can therefore receive exact-symbol identity weight when they match local variables or test constants.
2. `FACT` V1's low-value list does not include many connective/common task terms seen in failures (`active`, `after`, `from`, `one`, `source`, `output`, `when`). Trailing punctuation can also produce dotted-identifier signals such as `generation.`.
3. `FACT` Identity and lexical family caps flatten candidates once they match several generic signals. Sixteen tasks had a structural top-five score tie; stable tie-breakers then become more influential than task specificity.
4. `FACT` Graph expansion inherits relevance from the top 24 seeds. It preserves valuable cross-file paths, but noisy seeds can spread bounded yet still unhelpful test/import evidence.
5. `FACT` `relevantSymbols` is populated from symbol identity/component evidence, not from the enclosing symbol of a source lexical match. Correct files can therefore lack the symbol ranges Pack needs.
6. `FACT` Pack uses fixed role shares and item caps for every task and protects only the first useful candidate. This can retain several generic tests while dropping lower-ranked required implementations or documents.

`INFERENCE` The principal issue is not that lexical and structural evidence coexist. It is that V1 does not distinguish candidate-source provenance, signal ambiguity, task mode, or plan role strongly enough before fixed caps and section policies are applied.

## 12. Language and Category Findings

- JavaScript: one task, required-symbol recall `1.0 / 0 / 0` for lexical / structural / ContextForge at 8K. The file is present but the common `run` symbol is not coupled to file-level lexical evidence. This is one task, not a language-wide conclusion.
- TypeScript: aggregate required-symbol recall `.792 / .688 / .813`. The self-repository failures and common-symbol boosts dominate the weakness; curated TypeScript cross-file/test tasks often succeed.
- Python and mixed: required-symbol recall is 1.0 for all systems at 8K. ContextForge packing usually improves precision, but `py-expired-lease-race` shows the improvement is not uniform.
- Configuration: ContextForge `.75` versus lexical `1.0` required-symbol recall because the package-smoke `run` symbol is missing, not because all configuration discovery fails.
- Concurrency: `.5` required-symbol recall for all systems; the Python case succeeds, while the self-index case fails at allocation after noisy ordering.
- Bug fix: required-symbol recall is 0 for the single stale-source ownership task. One task cannot support a general bug-fix rate claim.

## 13. Evidence-backed Product Conclusions

- `FACT` V1 structural ranking underperforms lexical ranking in aggregate retrieval on this frozen dataset.
- `FACT` V1 Pack provides positive, non-uniform recovery over structural whole-file at some budgets and tasks.
- `FACT` Exact identity, file graph/test relationships, verified lexical evidence, and hard-budget ranges each have preserved success cases.
- `INFERENCE` V2 should improve fusion and planning rather than remove lexical or graph evidence.
- `INFERENCE` No observed primary failure requires a mandatory embedding, provider, cloud service, or persisted full-text index.
- `HYPOTHESIS` Ambiguity-aware task analysis, lexical-to-symbol ownership, complementary candidate sources, and plan-aware allocation will improve the same frozen benchmark without sacrificing exact/cross-file controls.

## 15. Edge-case Audit

- CamelCase, PascalCase, snake_case, kebab-case, dotted identifiers, paths, filenames, quoted literals, numbers, and CJK tokens are normalized by V1 and covered by unit tests; CJK-to-English translation is not implemented or benchmarked.
- Exact identities are strong controls, but common names such as `run`, `active`, `after`, and `source` expose collision/ambiguity problems.
- Error identifiers and technical phrases are supported (`BEGIN IMMEDIATE`, `SELECT FOR UPDATE`), but the frozen tasks do not isolate every form.
- Mirrored test names/direct imports work on curated tasks; ambiguous same-name relationships remain heuristics.
- Cycles, high-degree hubs, documentation hubs, generated/dependency exclusions, stale/deleted source, malformed ASTs, partial parses, and ignored sensitive files already have bounded production/security tests. V2 must consume only the same eligible snapshot and cannot improve recall by reopening excluded content.

## 16. Rejected or Deferred Directions

- Retuning `contextforge-structural-v1`: rejected because it would mutate frozen V1 and invite benchmark overfitting.
- Replacing production retrieval with `lexical-full-file-v1`: rejected because the baseline is benchmark-only and would discard structural wins and production Pack semantics.
- Mandatory embeddings, LLM query rewriting/reranking, vector storage, or cloud services: deferred; not required by observed failures and inconsistent with the V0.2 core boundary.
- Full LSP/compiler semantic index: deferred as disproportionate to the evidence and package footprint.
- SQLite FTS/source persistence: deferred; current generation-verified scan preserves privacy and no new performance result proves FTS necessary.
- V0.3 Workbench, pins/excludes, UI, review mode, multi-repo, agents, and live watching: out of scope.

## 17. Risks and Limitations

- The dataset is small, includes six self-repository tasks, and has no external-human Gold review.
- Required rank statistics are unweighted record counts, while published recall is task-macro averaged; they answer different diagnostic questions.
- Candidate diagnostics replay current V1 production code against the pinned corpora and reconcile selected identities, but the committed reference remains the authoritative score artifact.
- The benchmark does not execute coding agents or measure task success.
- Performance evidence is one Windows host with three repetitions and is not an SLA.
- There is no live stale-source mutation, large external repository, hosted cross-platform diagnostic replay, semantic retrieval, or CJK-to-English benchmark evidence.
- Qualitative root-cause confidence is evidence strength, not a probability.

The machine-readable classifications are reviewable and intentionally preserve negative findings. Any future methodology, metric, Gold, or task change belongs to a separately versioned benchmark or targeted regression set, never a silent edit to benchmark V1.
