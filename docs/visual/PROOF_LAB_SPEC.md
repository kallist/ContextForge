# RepoBound Proof Lab Specification

## Purpose

Proof Lab answers: **What does RepoBound actually produce?** It is a static Pages
experience built from deterministic, recorded RepoBound fixture output. It presents
artifacts and boundaries, not marketing claims.

## Route and shell

Published route: `https://kallist.github.io/RepoBound/proof/`. The shell shares the
Studio token system, typography, warm light surfaces, path treatment, and restrained
amber state language. It has no remote runtime dependencies.

## Exactly three cases

1. **Task Context — Fix session race condition.** Show actual task, budget, selected
   and dropped counts, key selected files, and Snapshot.
2. **Review Context — Review a meaningful tracked Git change.** Show actual changed
   files, captured structural/heuristic relations, bounded context, and limits.
3. **Context Debugging — Why was a test dropped?** Show the recorded drop reason,
   Include control, rebuilt Capsule, and factual `DROPPED → SELECTED` transition.

## Evidence artifacts

Proof data is generated by a checked-in script from the real application path and a
synthetic deterministic fixture. Static JSON may be checked in only when it records
that execution and contains no source bodies, machine paths, timestamps, secrets, or
invented metrics. Preview images are generated from the same values.

## Pages

The home page leads with “Real context compilations. Inspectable evidence.
Reproducible state.” Cases use large previews and editorial spacing rather than a
dashboard grid. Case pages tell a short TASK → CONTEXT/WHY → CONTROL → RESULT story
and link to Context, Exact Context boundary, Snapshot, and replay receipt where real.

## Acceptance

- Desktop and 390px mobile have no horizontal overflow or broken assets.
- All three cases have traceable real fixture data.
- No unsupported completeness, accuracy, savings, productivity, or success claim.
- The site remains static and works with CSP `default-src 'none'` plus local images/CSS.
