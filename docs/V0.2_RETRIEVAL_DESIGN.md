# ContextForge Retrieval V2 Design

## 1. Status

**DESIGN READY / NOT IMPLEMENTED**

This is an implementation contract for V0.2. It does not claim that V2 improves retrieval. `contextforge-retrieval-v2`, `contextforge-pack-v2`, `TaskAnalysis`, and `ContextPlan` are proposed identities/contracts and do not exist in production at this status.

## 2. Goal

Make ContextForge context selection measurably better on the unchanged frozen benchmark by:

- retaining exact identity, verified lexical, graph, test, documentation, and weak Git strengths;
- preventing common/ambiguous task terms from masquerading as strong exact identity;
- turning file-level lexical evidence into bounded symbol ownership evidence;
- fusing complementary candidate sources into one explainable file envelope;
- expressing task-specific context needs without choosing files in the planner;
- letting Pack honor those needs under the same final serialized hard budget.

## 3. Non-goals

V2 core does not require embeddings, an LLM, a provider key, a vector database, FTS/source persistence, cloud services, compiler-complete references/calls, a Web UI, Workbench controls, agent execution, multi-repository search, new languages, live watching, review mode, or V0.3/V0.4 features.

V0.2-01 implements none of this design. It does not modify V1 weights or use the benchmark lexical baseline as production code.

## 4. Architecture

```text
CLI / MCP adapters
        ↓
Application Search / Pack use cases
        ↓
Raw task
        ↓
TaskAnalysis ───────────────┐
        ↓                   │
ContextPlan                │
        ↓                   │
Candidate sources          │ one active RepositoryIndexSnapshot N
  ├─ identity              │ + generation-verified source bytes for N
  ├─ lexical               │
  ├─ symbol ownership      │
  ├─ file structural       │
  ├─ test/documentation    │
  ├─ bounded impact        │
  └─ weak Git              │
        ↓                   │
Candidate fusion ◀─────────┘
        ↓
Ranking V2
        ↓
Bounded expansion
        ↓
Ranked file envelopes with relevant symbols
        ↓
Plan-aware Pack V2
        ↓
Final serialized hard-budget Context artifact
```

The design extends the existing dependency direction. Core contracts remain independent of CLI, MCP, SQLite, Tree-sitter, filesystem/Git implementations, providers, and UI. Application code coordinates the snapshot and source-reader ports. Adapters only translate input/output.

### Compatibility with V1

- V1 identities and behavior remain executable: `contextforge-structural-v1`, `contextforge-pack-v1`, and `contextforge-generic-v1` 1.0 are immutable benchmark strategies.
- V2 must not copy Search into CLI and MCP. Both adapters call the same application pipeline.
- Shared source verification or snapshot-loading helpers may be extracted only with parity tests proving V1 output is unchanged.
- The benchmark can select V1 or V2 internally. No public strategy flag is required for the first implementation slice.
- Production default does not switch to V2 until the full V0.2 gate passes.

## 5. Domain Contract Principles

Every new contract is:

- deterministic and serializable;
- bounded with stable ordering and identities;
- repository-relative only;
- explicit about structural facts versus heuristics;
- free of source bodies and secrets when persisted or emitted as diagnostics;
- incapable of bypassing repository eligibility, snapshot, or budget policy.

The user task is untrusted data. Production may retain raw task text request-scoped for the existing output contract, but it must not persist tasks, TaskAnalysis, plans, candidates, or evidence in SQLite.

## 6. Proposed `TaskAnalysis`

```ts
interface TaskAnalysis {
  schemaVersion: "1.0";
  strategy: "contextforge-task-analysis-v2";
  task: string; // request-scoped untrusted data; never persisted
  action: "FIX" | "CHANGE" | "REFACTOR" | "TEST" | "REVIEW" | "UNDERSTAND";
  mode:
    | "EXACT_TARGET"
    | "BEHAVIORAL"
    | "TEST_FAILURE"
    | "CONFIGURATION"
    | "CONCURRENCY"
    | "ARCHITECTURE"
    | "GENERAL";
  signals: readonly TaskSignal[];
  concepts: readonly TaskConcept[];
  riskSignals: readonly TaskRiskSignal[];
  diagnostics: readonly string[];
}

interface TaskSignal {
  id: string; // stable hash/ordinal of kind + normalized value + provenance
  kind:
    | "PATH"
    | "FILE_NAME"
    | "QUALIFIED_SYMBOL"
    | "SYMBOL"
    | "ERROR_IDENTIFIER"
    | "TECHNICAL_LITERAL"
    | "CONFIG_KEY"
    | "NATURAL_TERM"
    | "CJK_TERM";
  value: string;
  normalized: string;
  provenance: "EXPLICIT" | "DERIVED";
  derivedFrom: string | null;
  specificity: "EXACT" | "TECHNICAL" | "GENERAL";
  ambiguity: "UNKNOWN" | "UNIQUE" | "COLLIDING";
}
```

`TaskConcept` is a small bounded enum justified by the frozen tasks: `STATE_MUTATION`, `CONCURRENCY`, `TRANSACTION_OR_LOCK`, `CONFIGURATION`, `TEST_BEHAVIOR`, `API_BOUNDARY`, `DOCUMENTATION`, `PACKAGING`, and `STALE_SOURCE`. It is not a general natural-language ontology.

`TaskRiskSignal` records an evidenced concern such as concurrency, stale-source, configuration validation, or public contract. It does not increase rank by itself; it informs the plan and can select source families/roles.

### Deterministic analysis rules

- Preserve current casing/path/identifier decomposition and technical literal handling where valid.
- Strip trailing punctuation before classifying dotted identifiers.
- Do not treat `NATURAL_TERM` as exact symbol identity without repository collision analysis.
- Record action/mode evidence and precedence. Exact identifiers do not erase a concurrent or test-failure mode.
- At most 256 signals, 16 concepts, 16 risk signals, and 32 diagnostics.
- No synonym model, network call, shell, `eval`, repository code execution, or hidden query rewrite.
- If analysis is ambiguous, choose `GENERAL`/`UNKNOWN` and retain diagnostics; never fabricate intent.

## 7. Proposed `ContextPlan`

```ts
interface ContextPlan {
  schemaVersion: "1.0";
  strategy: "contextforge-context-plan-v2";
  mode: TaskAnalysis["mode"];
  sections: readonly PlannedSection[];
  focusSignalIds: readonly string[];
  diagnostics: readonly string[];
}

interface PlannedSection {
  role:
    | "PRIMARY_IMPLEMENTATION"
    | "STATE_OWNER"
    | "CALLER_OR_DEPENDENT"
    | "TEST"
    | "CONFIGURATION"
    | "DOCUMENTATION"
    | "REPOSITORY_INSTRUCTION";
  priority: "REQUIRED" | "PREFERRED" | "OPTIONAL";
  minimumItems: 0 | 1 | 2;
  maximumItems: number;
  acceptedEvidenceSources: readonly CandidateSourceId[];
  rationale: string;
}
```

The plan states what kinds of context are useful. It never contains paths, symbol IDs, scores, source bytes, or a preselected file. `REQUIRED` means Pack should attempt a bounded minimum when evidence exists; it does not authorize budget overflow or unsafe selection.

Initial deterministic templates:

| Mode | Required | Preferred | Optional |
|---|---|---|---|
| Exact target | target implementation | parent/owner, direct references, tests | docs/config |
| Concurrency | implementation + state/transaction boundary | callers/dependents + concurrency tests | architecture/config |
| Test failure | failing test + exercised implementation | state owner/dependencies | docs/config |
| Configuration | config/schema/manifest + validator/consumer | tests/defaults | docs |
| Architecture | requested document/decision | implementation evidence | tests/config |
| Behavioral/general | primary implementation | state owner, callers, tests | docs/config |

When no candidate exists for a required role, Pack reports `PLAN_ROLE_UNSATISFIED`; it does not silently substitute an unrelated file.

## 8. Candidate Sources

```ts
type CandidateSourceId =
  | "IDENTITY"
  | "VERIFIED_LEXICAL"
  | "SYMBOL_OWNERSHIP"
  | "FILE_STRUCTURAL"
  | "TEST_DOCUMENTATION"
  | "IMPACT"
  | "GIT";

interface CandidateSource {
  readonly id: CandidateSourceId;
  retrieve(context: CandidateSourceContext): readonly CandidateEvidence[];
}
```

The conceptual interface belongs at the application/core boundary; concrete source access remains through existing ports. Sources do not receive Gold and do not assign final rank.

### Identity

Exact repository path, filename, qualified symbol, unambiguous symbol, error identifier, and technical literal. Natural words matching many symbols are collision-aware lexical/symbol evidence, not exact identity.

### Verified lexical

Reuse the generation-verified source reader and V1 caps. Produce match locations, distinct signal coverage, occurrence saturation, and technical/general provenance. Do not persist terms or source.

### Symbol ownership

Map a verified lexical match location to the smallest containing parser symbol and its parents. The containment is a structural fact when ranges come from the selected generation. A lexical match does not make every symbol in the file relevant.

### File structural

Reuse generation-bound import, reverse-import, test, and documentation edges. Structural evidence should answer “what else matters?” after high-quality seeds, not replace direct task evidence.

### Test/documentation

Reuse direct import/exact path edges as facts and existing naming/module relations as heuristics. Preserve confidence and derivation.

### Impact

Initially derive bounded dependents, direct importers, referenced owners, configuration consumers, and tests from existing data/transient selected-source analysis. Do not implement a compiler-complete call graph.

### Git

Git remains weak, generation-bound, and unable to create a candidate. No research finding justifies increasing its influence.

## 9. Proposed `CandidateEvidence`

```ts
interface CandidateEvidence {
  id: string;
  source: CandidateSourceId;
  family: "IDENTITY" | "LEXICAL" | "SYMBOL" | "STRUCTURAL" | "PLAN" | "GIT";
  target: { file: string; symbolId: string | null };
  taskSignalId: string | null;
  matchKind: string;
  confidence: number; // 1.0 fact; <1.0 heuristic
  derivation: "STRUCTURAL" | "HEURISTIC" | "VERIFIED_SOURCE";
  location: { startLine: number; endLine: number } | null;
  sourceCandidate: string | null;
  rawFeature: number | string | boolean;
  explanation: string;
}
```

No evidence record contains source text. Confidence is provenance/derivation confidence, not probability that a file is relevant. Raw feature values remain separate from final score contributions so ablation and explanations can distinguish discovery from weighting.

## 10. Candidate Fusion

Fusion uses one map keyed by canonical repository-relative file path.

1. Reject anything absent from the selected eligible snapshot.
2. Deduplicate evidence by source, target, task signal, derivation, location, and originating relationship.
3. Merge symbol evidence by stable symbol ID under one file envelope.
4. Count distinct task signals and distinct source families separately; repeated occurrences or multiple graph paths cannot inflate without caps.
5. Compute ambiguity/collision features from the snapshot. Ten `run` symbols are not ten exact targets.
6. Retain the best bounded relationship evidence and explanations; do not sum every path through a hub.
7. Assign plan roles after evidence fusion, without duplicating the file. A file has one primary role plus bounded secondary roles.

The output preserves V1's good property: one final envelope per file, with nested relevant symbols and a reconstructible explanation.

## 11. Ranking V2 Principles

V0.2-01 intentionally defines no final numeric weights.

### Intended relative ordering

1. Explicit exact qualified symbol/path/error/technical literal.
2. Explicit unambiguous symbol or basename.
3. Verified multi-term technical lexical coverage and lexical-to-owning-symbol evidence.
4. Complementary agreement across independent sources.
5. Direct structural facts from high-quality seeds: imports, reverse imports, direct test imports, exact document paths.
6. Confidence-labeled heuristics and distance-decayed impact evidence.
7. Weak Git tie-break contribution.

### Caps and ambiguity

- Retain family, per-signal, per-source, per-file, symbol, neighbor, depth, and global candidate caps.
- General natural terms cannot receive explicit-identity weight solely because a local variable has the same name.
- Collision count must be monotonic: making an identity more ambiguous cannot increase its identity contribution.
- Adding independent exact evidence cannot lower a candidate score.
- Repeating identical evidence cannot raise score after deduplication.
- Adding a graph path through a higher-degree hub cannot produce a larger inherited contribution than an otherwise equal lower-degree path.
- Git can never overtake a candidate supported by explicit exact identity.

Final weights belong to V0.2 implementation and frozen ablation, not this design document.

## 12. Symbol, Test, and Impact Relationships

| Relationship | V2 classification | Persistence for first slice | Reason |
|---|---|---|---|
| File imports file / reverse import | structural fact | reuse current schema | already generation-bound and reliable within supported resolver |
| Lexical match contained by symbol | structural fact when indexed range is valid | transient | derivable from verified bytes + current symbol ranges |
| Parent symbol contains symbol | structural fact | reuse current symbol parent field | already indexed |
| Test directly imports source | structural fact | reuse current edge | existing success evidence |
| Unique mirrored test/source name | heuristic | reuse current edge | useful but must keep confidence/evidence |
| Test references one unique symbol name | heuristic | transient first | needs measurement before schema cost |
| File directly depends on target | structural fact | reuse current edge | bounded impact context |
| Symbol references/calls symbol | heuristic with Tree-sitter-only evidence | transient research only | no compiler-complete binding |
| Symbol implements interface | not implemented initially | none | current parsers/resolver do not establish reliable semantics |
| Test covers symbol | heuristic | transient research only | coverage is not proven by import/name alone |

No new SQLite relationship is justified before transient evidence demonstrates quality gain and acceptable cost.

## 13. Pack V2 Interaction

Ranking remains the only relevance truth. Pack V2 does not rescore candidates; it uses plan roles, rank, evidence provenance, symbol/range options, cost, and redundancy to choose representations.

Proposed rules:

- preserve final serialized `estimatedPayloadTokens <= requestedBudget` under the named estimator;
- preserve one generation and read/hash/slice the same in-memory bytes;
- protect a bounded minimal set across required plan roles, not only the first candidate;
- allocate across plan roles dynamically rather than fixed global shares;
- use lexical-match locations to select enclosing symbols before generic prefixes;
- prefer complete small symbols/files and merge overlapping ranges as V1 does;
- record `PLAN_ROLE_UNSATISFIED`, `HIGH_PRIORITY_DROP`, role, rank, and exact drop reason;
- if the envelope plus one useful primary unit cannot fit, retain `BUDGET_TOO_SMALL`;
- if a plan role cannot fit but a useful safe pack can, return a truthful partial manifest rather than overflow;
- final deterministic eviction may downgrade/drop the lowest-value optional unit, but never unsafe/stale checks or the budget.

## 15. SQLite Implications

Preferred first-slice result: **no schema change**.

- TaskAnalysis, ContextPlan, candidate evidence, lexical match locations, lexical-to-symbol ownership, fusion, and rank are request-scoped.
- Existing files, symbols, parent ranges, imports, file graph, and Git signals are enough to test the principal hypotheses.
- Existing V0.1 schema-version-2 databases remain readable by V2 Search/Pack subject to current graph availability rules.

If later evidence justifies persisted symbol references, that is a separate migration design: new schema version, whole-generation derivation, atomic activation, old-schema read/reindex behavior, rollback, future-schema rejection, and migration tests. V0.2-01 authorizes none of it.

## 16. Snapshot and Concurrency Invariants

Mandatory sequence:

```text
Search loads complete generation N
→ every candidate source reads metadata from N
→ lexical/symbol ownership accepts only bytes whose hash matches N
→ fusion/ranking/plan use only N identities
→ Pack reads/hashes/slices N bytes once
→ concurrent Index may atomically activate N+1
→ current Search/Pack stays on N
→ later Search sees N+1
```

- No cross-generation evidence, lazy N+1 lookup, or auto-index.
- One `BEGIN IMMEDIATE` writer, bounded `INDEX_BUSY`, atomic activation, WAL reader snapshot, rollback, crash recovery, and future-schema rejection remain unchanged.
- Candidate sources are pure/read-only after the snapshot is loaded.
- Transient analysis cannot extend the writer transaction.

## 17. Security

Preserved invariants:

- Safe Repository Map eligibility before retrieval;
- built-in/dependency/generated/sensitive/ignored exclusions;
- symlink/junction/outside-root rejection;
- generation-verified lexical reads and stale exclusion;
- no repository source execution, shell interpolation, `eval`, upload, telemetry, model, or network requirement;
- no source/task/evidence/full-text persistence;
- no absolute path in public or benchmark diagnostic artifacts;
- bounded task/signal/evidence/candidate output;
- repository content remains untrusted when serialized.

New risks and controls:

- Task-derived modes can overinterpret input: record provenance, bound enum, use `GENERAL` on ambiguity.
- Match locations can reveal sensitive content indirectly: emit line ranges and signal IDs only, never matched source snippets.
- More evidence increases secret/explanation surface: source-derived explanations use type/count/path, not literal content unless the literal is already an explicit task signal and safe to display.
- Plan role labels cannot reopen excluded files or bypass stale checks.

## 18. Performance Bounds

V1 measured structural Search slower than lexical; V2 adds work and makes no speed claim.

Initial hard work bounds should not exceed V1 without a measured design review:

| Work | Initial V2 bound |
|---|---:|
| Task bytes / signals | 16 KiB / 256 |
| Per-signal identity candidates | 32 |
| Verified lexical scan | 10,000 files / 64 MiB |
| Lexical candidates | 120 |
| Primary candidates | 200 |
| Graph seeds / depth / neighbors | 24 / 2 / 24 |
| New expanded / final internal files | 128 / 256 |
| Evidence per candidate | 64 direct + 32 relationship |
| Relevant symbols per file | 32 |
| Pack input / verified source | 64 files / 32 MiB |

Future measurement separates TaskAnalysis, plan construction, each candidate source, fusion, expansion, ranking, range selection, Pack planning, serialization, total Search, and total Pack. Reaching a cap is an explicit partial diagnostic, never an unbounded fallback.

## 19. Failure Handling

| Condition | Required V2 behavior |
|---|---|
| Missing/corrupt/future index | existing explicit error; no fallback scan presented as indexed truth |
| Stale/deleted/added source | exclude mismatched bytes; `STALE`/partial diagnostics; never auto-index |
| Parser unavailable/degraded | preserve safe verified lexical file evidence; do not fabricate symbols |
| Partial repository/lexical scan | bounded candidates plus explicit partial status/cap diagnostic |
| Ambiguous symbol | downgrade/labeled collision; no arbitrary exact resolution |
| Unresolved/ambiguous import | retain status; do not create structural fact |
| Incomplete graph | use available direct/lexical evidence and report graph limitation |
| Unsupported language | safe lexical fallback where V1 permits; no semantic promise |
| No candidate | explicit no useful candidate/error; no unrelated default context |
| Tiny budget | unchanged `BUDGET_TOO_SMALL` boundary |
| Oversized/empty task | existing explicit validation errors |
| Concurrent writer | Search/Pack stays on N; writer keeps bounded `INDEX_BUSY` |
| Unsatisfied plan role | partial diagnostic; no budget or safety bypass |

## 20. Benchmark V2 Plan

Formal systems:

```text
lexical-full-file-v1
structural-full-file-v1
contextforge-v1
contextforge-v2
```

The frozen task, snapshot, Gold, budgets, estimator, serialization accounting, safety boundary, and V1 metric definitions remain identical. The 480-case quality matrix adds 120 V2 cases; it does not rewrite the 360 V1 cases or replace historical results.

Primary metrics remain File/Symbol Recall@K, required file/symbol recall at budget, overall Gold recall, Gold-range precision, noise, payload tokens, matched-recall tokens/reduction, and latency.

New diagnostic metrics are versioned additions, not V1 redefinitions:

- first/median required file and symbol rank;
- lexical-only, structural-only, and overlap discovery;
- candidate-source contribution and distinct-signal coverage;
- pre-Pack symbol coverage and post-Pack loss;
- high-priority/role drop counts;
- taxonomy miss rate;
- per-stage timing and cap events.

### Bounded ablation

Run all 24 tasks at 8K for research ablations; run only baselines and final V2 across all five budgets in ordinary formal comparison.

1. TaskAnalysis + identity + verified lexical.
2. Add existing file structural graph.
3. Add lexical-to-symbol ownership.
4. Add test/bounded impact evidence.
5. Add ContextPlan-aware role assignment.
6. Add Pack V2.

Each step changes one signal family or planning boundary so gains can be attributed. Do not publish a result from whichever ablation happens to win.

### Targeted regression set

A separate, small `retrieval-v2-regression` set may cover common-symbol ownership, ambiguous natural terms, concurrency allocation, architecture documents, test linking, configuration consumers, and stale-source mutation. It is a correctness gate, not a replacement quality benchmark and cannot alter `contextforge-dataset-v1`.

## 21. Proposed V0.2 Acceptance Gates

**DESIGN TARGETS — NOT YET MEASURED**

### Integrity and correctness

- Dataset/Gold/reference V1 hashes unchanged; 480 expected cases present.
- Zero final-budget violations in every V2 case.
- Repeated deterministic V2 quality artifacts are byte-identical.
- V1 selected results remain byte/semantic compatible.
- All existing security, stale-source, concurrency, package, CLI, and MCP tests pass.

### Aggregate quality at 8K

- Required-file recall: at least V1 `.917`.
- Required-symbol recall: at least `.900`, strictly above V1 `.864` and lexical `.848`.
- Overall Gold recall: at least V1 `.871`.
- Gold-range precision: at least V1 `.193`; no recall gain may be called a win with lower aggregate precision.
- Noise: no worse than V1 `.807`.

These thresholds are fixed before the formal V2 score. Failure is reported, not tuned away.

### Regression protection

- Four exact-symbol controls retain complete required recall.
- Cross-file and test-failure category required-symbol recall does not regress from the V1 8K result.
- None of the 19 task-level V1 successes gains a new required-context miss.
- Each of the four former 8K misses strictly improves its missing dimension; at least three reach complete required recall.
- `self-output-publish-race` retains complete recall and precision is no lower than lexical minus `.01`.

### Token/performance guardrails

- At matched 90% required-symbol recall, V2 must reach at least the V1 task count and must not have negative macro token reduction versus lexical.
- Paired V2 payload tokens must not regress more than 5% against V1 without a separately approved quality tradeoff.
- Median warm Search and Pack on both existing performance corpora should be no more than 1.5× V1; any excess blocks a performance claim and requires design review.
- Existing caps cannot be silently raised to pass recall.

## 23. Migration and Backward Compatibility

- No database migration in the proposed next slice.
- Existing CLI arguments and MCP tool names remain unchanged.
- Public Search/Pack schema may add optional analysis/plan strategy identities and diagnostics; removing/renaming V1 fields requires a separate compatibility review.
- V1 remains benchmark-selectable indefinitely for historical comparison.
- V2 default activation, if later authorized, is a release decision after the full gate—not an incidental code-path change.
- `contextforge-generic-v1` remains the estimator until a separately versioned tokenizer decision.

## 24. Open Questions

These questions are bounded implementation measurements, not hidden architectural gaps:

1. Which small low-value/common-term table and repository collision threshold best prevents false exact identity without weakening explicit symbols?
2. Should lexical-to-symbol ownership prefer the smallest containing symbol only, or retain one bounded parent chain?
3. How should plan-role minima trade off when two required roles cannot both fit above the V1 minimum useful-pack boundary?
4. Can transient symbol-reference evidence improve the frozen tasks enough to justify any later persistence?
5. Which V2 fields can be added to public Search/Pack JSON without a schema-version increment?
6. Does V2 remain within the proposed 1.5× performance guardrail under the existing caps?

None requires a mandatory model, cloud dependency, full product rearchitecture, or V0.1 schema rewrite.
