## Implemented experiment

`src/core/packing/context-plan.ts` derives `contextforge-pack-plan-v1` from existing TaskAnalysis action/mode only. The prior retrieval ContextPlan is untouched. Four roles (PRIMARY, IMPACT, VALIDATION, SUPPORT) use REQUIRED/HIGH/NORMAL priorities; no paths, task values, candidate IDs or Gold enter the plan. Actual mode/action behavior and pre-evaluation policy are in ADR-011.

`src/core/packing/pack-v2.ts` protects a fitting direct anchor, attempts one item for each uncovered important role, shares remaining budget globally, and attempts enrichment. It retains the 64-candidate/source limit and the same aggregate 18 ordinary-file capacity as V1. Role opportunities are soft; there are no reserved token percentages. Diagnostics count global selections and unused opportunities instead of inventing token transfers between nonexistent accounts.

`src/application/build-context-pack-v2.ts` uses the shared relationship-enabled retrieval path, one generation snapshot, safe eligible entries, hash-verified transient source, existing interval/Markdown helpers, and the unchanged serializer and generic-v1 estimator. Every attempted selection measures the complete Markdown; final serialization is checked again. Symbol cores have bounded one/two/six-symbol options, small whole-file options, overlap merging, and optional surrounding lines. Each selected file is serialized once even if it covers several roles. Provenance, role reasons, options, selection events and drops stay source-free.

Stable drop reasons: GLOBAL_BUDGET, SAFETY_LIMIT, REDUNDANT_RANGE, STALE_SOURCE, UNSUPPORTED_CONTENT, NO_USEFUL_RANGE. Generation mismatch is an error; unavailable verified source cannot be promoted by the planner.

No database schema, migration, writer behavior, public API, CLI/MCP default, Pack V1, estimator, retrieval weights, relationship bounds or shadowing semantics changed. No embeddings, LLM compression, new retrieval, deeper relationships, Capsule, Workbench, V0.3 or V0.4 work was implemented.

### Causal regression and semantic invariant

The new generic test uses a selected validation item (200 tokens), a higher-ranked direct implementation (300 tokens), and a lower-ranked large secondary guide (1600 tokens), with a 2000-token total budget including a 50-token envelope. The initial policy selected the guide and excluded the implementation: **1 test, 1 failure** before correction. The same required implementation-survival assertions pass after correction. No frozen task/repository/filename appears in this regression.

`direct-context-priority-v1` separates four-role coverage from target facet and evidence directness. Facets reuse existing category/language/symbol facts: IMPLEMENTATION, VALIDATION, CONFIGURATION, DOCUMENTATION, OTHER. Directness uses existing unambiguous evidence: IDENTITY, OWNED_SYMBOL, VERIFIED_LEXICAL, INDIRECT. A test relationship can add VALIDATION role to production code without turning it into a validation facet.

Ordering is directness, discrete plan priority, existing retrieval rank, marginal uncovered-role novelty, compact cost, canonical path. Stronger direct candidates receive a compact opportunity before a secondary role can jump ahead. The strongest evidence tier supplies the anchor; task facet breaks ties within that tier. Target facet remains independently unsatisfied when a different PRIMARY facet was selected. TEST/test-failure, configuration, architecture/understand/review, and implementation actions use their corresponding facet; neutral and general/default-CHANGE use conservative direct ordering. The existing task analyzer is unchanged, including its GENERAL-mode classification of some explicit FIX actions.

All selections try the cheapest existing useful representation before enrichment. No role percentages, numeric weight search, document penalty, new ranges, wider caps, retrieval changes or schema changes were introduced. Role novelty still resolves equivalent directness/priority/rank ties. Unavailable opportunities consume zero tokens, and larger budgets may still include large support after direct context. Exact serialized budget checks remain authoritative.

### First implementation-only optimization

The application creates one immutable render item per candidate range option. A request-local WeakMap reuses its exact `renderContextItem` result across tentative selections. The existing serializer accepts an internal item-render callback, defaulting to its original implementation, so Pack V1 remains on the unchanged rendering path.

The cache retains at most 321 fragments and 1,048,576 UTF-16 characters (up to 2 MiB character data plus bounded object overhead). Reaching either memory bound causes exact recomputation, not rejection or changed selection. No persistent cache, source-body diagnostics or additional source reads are introduced.

Every tentative pack still uses the complete Markdown and unchanged estimator. The final pack is independently rendered with the original uncached item renderer, then independently estimated. No additive token approximation or incremental feasibility accounting was introduced. This avoids changing the estimator's global rounding behavior.

The ordering component remains O(N² log N) in the frozen corrected selector. Fragment rendering changes from repeated work per occurrence to once per cached immutable option, with exact fallback at the memory cap. Full string assembly and estimation remain O(A * P), where A is the number of attempts and P their serialized size. This is a constant-factor reduction, not the proposed linear-time total-cost model.
